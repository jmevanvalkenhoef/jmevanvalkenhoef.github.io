Shared Board: a kanban board for a person and an AI agent

Most people work with AI through a chat window. I wanted a shared space instead, where a person and an agent work on the same thing and each can see what the other does. The board is that space. The experiment on top of it asks how the design of the agent's tool changes its work.

How it works

The board is a small web app. You work in the browser: drag cards, rename them, add new ones. The agent works through a command-line tool called board, with commands like board show todo and board move 4 doing. Both go through the same server, which records every change as an event in a log, together with who made it. The board is computed from that log, and every change is pushed to each open page as it happens. So when the agent moves a card, you see it slide into its new column with an orange edge, and you can move it back.

The code keeps the board logic in one place. The rules for what a change does are pure functions, and the browser runs the same files as the server. The CLI prints through a small interface, so the experiment could swap its output style without touching any command.

The experiment

An agent's tool is usually designed for people. I built three versions of the same CLI: a plain one, an agent-friendly one that explains its rules and reports what each change did, and a forgiving one that also accepts the commands agents tend to guess. Then I gave three Claude models 18 tasks each, from moving a few cards to sorting a column by priorities hidden in the descriptions.

For every run, a harness starts a fresh board, gives one task to Claude Code running headless, and lets a script compare the final board with the expected one. The agent can only run board. Each run records success, tool calls, failed commands and tokens. A hierarchical Bayesian model then separates the CLI's effect from how hard each task is.

What I found

The agents finished almost every task with every version. The differences were in the detours they took on the way. Accepting the commands agents guess brought their wrong commands down to about a third, for every model. More helpful output saved tool calls, but it made Sonnet about 19% more expensive, because Sonnet barely needs the help and the longer text stays in its context. For the oldest, weakest model the same output saved tokens. The choice of model mattered far more than any design: Haiku 5.5 did a typical task for about an eleventh of Sonnet's cost.

Before running five new tasks, I committed the model's predictions for them. All 90 held-out runs landed inside the predicted ranges. The write-up says what that test does and does not show, and also covers a flaw in my first round and a mistake in my own help text.
