FIPS Lab: breaking a mesh network on purpose

Most connections on the internet depend on third parties for identity: DNS for names and certificate authorities for trust. FIPS is a young network that does without them. Every node is identified by its own key, and the nodes route traffic among themselves without a central server. Without anyone in the middle, the network has to route around failed links by itself, and I built a lab to measure how well it does that.

The question

I wanted to know how long it takes, after a link in a FIPS mesh breaks, before traffic flows along another path, and whether that always happens. Answering it requires cutting the same link in the same way many times, keeping the runs in which traffic never came back, and seeing what each node believes about the network during the cut.

What I built

A topology file describes the mesh, and the lab starts one Docker container per FIPS node and one Docker network per link. Because every link has its own network, a cut, a delay or packet loss affects exactly one link. Faults can be injected from the command line, from scripted scenario files, or by clicking a link in the browser.

A collector reads every node's control socket once a second and streams the result to a D3 page, where you can watch the spanning tree change after a cut. Scenario runs record how long each wait took. When a wait times out, the run is stored as a censored measurement with the timeout as a lower bound. Without that, the stuck cuts would have dropped out of the data.

What I found

In most runs, traffic rerouted within the dead-link timeout plus about a second. Two results were unexpected.

In the first five minutes after start-up, traffic can get stuck. In 7 of 10 cuts made 90 s after start-up, replies looped between two nodes until their hop limit ran out, and no traffic got through for minutes. On a mesh that had been running for a while, 0 of 38 cuts got stuck. I traced this in the Rust source to an anti-poisoning rule: a node trusts routing data it has verified itself for 300 s and ignores corrections during that time.

A repaired link can also stay unused for a while. After a link is declared dead, the interval between reconnect attempts doubles each time, so a healed link waited up to 76 s before FIPS used it again.

Seeing the timer from outside

The second write-up asks whether the measurements alone could have found that timer. A censored mixture model in PyMC, fitted to every cut, places it at 301.4 ± 1.3 s. The write-up shows how much each part of the data contributes, and then uses the model to predict the outcome of new cuts. In a separate 25-minute run, all 5 new cuts fell inside the predicted range.
